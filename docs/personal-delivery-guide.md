# 个人使用：接入、发布与回滚

## 第一次接入

先按 README 启动 DevPilot，创建管理员。业务 Linux 服务器上安装 Docker、Dokploy 和 Agent，确认 Agent 在线；DevPilot 和业务服务可以在同一台机器，也可以分开。Agent 主动连接 DevPilot，DevPilot 需要能访问 Dokploy API，GitHub 需要能访问签名回调入口。

进入发布中心的“自动接入新项目”，输入仓库授权及部署平台 Key。当前以根目录已有 Dockerfile 的单服务项目为主。确认端口、健康路径及必要变量，审阅生成配置后开始。接入任务完成后审阅并合并 PR，不代表应用已经上线。

接入前会检查可访问的项目/服务器以及 Dokploy 管理的应用端口冲突；非 Dokploy 进程占用、防火墙和 DNS 仍需核对。Swarm 发布端口来自 Service，容器内部的 `8080/tcp` 不等于服务器已开放 8080。`Swarm ingress :18088→8080/tcp` 表示访问服务器 18088，转到容器 8080。

## GitHub 新版发布流程

1. 将代码推送至配置的默认分支。
2. 等待 `quality`、`security`、`image` 成功。此时 production 跳过是预期行为。
3. 记录该次成功 push 的 Run ID（Actions 详情 URL 最后的数字）。
4. 打开同一 workflow 的 Run workflow，选择默认分支，在 `build_run_id` 填入该 Run ID，人工确认。
5. 发布任务检查同仓库、同 workflow、默认分支、成功 push 状态和构建凭证中的 commit/digest，随后发送签名回调。不会重新构建，不会退回到 tag。
6. 在 DevPilot 检查最终部署状态。CI 成功只证明回调任务完成，不等于服务器已健康。

构建凭证保留 90 天。凭证过期、构建取消/失败、选择 PR 构建或错误 workflow 都不应发布。新模板不会静默替换既有仓库的 workflow，需要通过正常仓库变更更新。

## 如何判断上线成功

`TRIGGERED` 表示已请求平台部署；`VERIFYING` 表示平台完成、仍等待运行证据；`HEALTHY` 才表示平台完成、关联容器运行目标镜像，并且新的健康探测通过。

检查应用版本、镜像、容器、健康时间及部署日志。HTTP 2xx 的 JSON `status` 当前识别 UP、HEALTHY、OK（不区分大小写）；明确 DOWN、degraded 等失败状态不会因 HTTP 200 被放行。

## 回滚

人工回滚：在发布历史中选择该应用的已健康版本，核对镜像后点击回滚并确认。回滚会创建独立部署任务，再次验证运行镜像和健康；不要只看按钮提示就认定恢复。

自动回滚：新接入默认关闭。明确启用“健康检查失败时自动回滚”后，失败发布才尝试回到上一健康镜像。没有上一健康版本时不会创建回滚；回滚自身失败不会无限循环，应检查日志并人工处理。

镜像回滚不恢复数据库、文件或数据卷。破坏性数据库迁移必须由业务提供兼容策略和备份。

## 常见故障

- Dokploy 401：检查 Key 有效期、权限和请求限额。v0.30.3 的默认每天 10 次配额会在自动接入时耗尽，平台日志可能显示 Rate limit exceeded。
- GHCR 拉取失败：检查包仍为 private、拉取凭据具备读取权限；Actions 推送成功不证明目标服务器能拉取。
- 回调 401：检查签名密钥和 Secret 所属 Environment；轮换后必须同步 CI。
- 回调网络失败：云端 Actions 无法访问本机 localhost。临时隧道只能用于验收，需保持运行且只暴露签名回调路由。
- 容器启动但不健康：检查目标机上的健康路径、服务器发布端口、监听地址、启动依赖和响应内容。
- 找不到构建凭证：选择同一 workflow 的成功 push Run ID，不要填写手动发布任务的 Run ID。

## 本地实验结束

停止临时隧道，撤销临时 Dokploy Key，移除测试仓库的回调 Secrets，清除临时 Registry 凭据及本地测试凭据文件。清理前记录测试应用和凭据的精确范围，不删除既有业务资源。清理后再次发布前必须重新配置授权和回调。

当前真实验收记录见 [本地验收记录](local-e2e-2026-09-05.md)。GitLab、Coolify、生产网络及未执行的回滚场景不能借用 GitHub/Dokploy 的测试结果声称已通过。
