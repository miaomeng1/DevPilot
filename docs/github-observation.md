# GitHub 状态核对与回调排查

本文对应当前工作树功能；已安装旧版本可能没有这些入口。隔离平台已升级到 V38，观察器配置已验证升级、重启和独立恢复后的持久化。真实 GitHub 自动核对与丢回调恢复仍未完整验收；已有 recover_build 运行只证明原始制品检查和幂等补报，不证明曾发生回调丢失。版本及验证范围见 [验收记录](stability-validation.md)。

## 先分清三种状态

- GitHub 任务状态：某次运行是在排队、运行、失败、取消还是成功。
- DevPilot 构建证据：测试、扫描结果与原始镜像 digest 是否完整上报。
- 应用运行状态：部署的新镜像是否实际运行并通过健康检查。

三者不能互相替代。核对到 GitHub 成功不会自动补齐发布证据，更不会跳过人工确认。

## 临时核对一次，不保存 Token

1. 使用管理员或开发者账号进入 CI/CD 发布中心，选择 GitHub 应用。
2. 展开“核对 GitHub 构建 · Read-only check”。
3. 选择具体构建。当前入口仅接受 `build:github-运行ID-运行次数` 格式的 GitHub push 记录，并核对仓库、commit、分支和运行次数。没有符合条件的记录时入口不会出现。
4. 填写能读取该仓库 Actions 的 GitHub Token，点击“只读核对 Check”。不要填写 GHCR 拉取密码、Dokploy Key 或 DevPilot 回调密钥。
5. 查看结果与核对时间。此操作不修改本地流水线状态、不重跑 GitHub 任务、不部署。

输入会在发送、关闭或切换应用后清空，不写入浏览器 localStorage/sessionStorage。关闭页面只能使页面忽略迟到结果，不能保证服务端已经发出的请求被取消。请通过 HTTPS 访问非本机部署的平台，不要把 Token 发在聊天、工单或截图里。

## 启用定期核对

1. 管理员在同一应用展开“自动核对设置 · GitHub observer”。开发者和只读用户不能管理保存的凭据。
2. 刷新配置，确认当前是正确的仓库和分支。
3. 输入仓库查询 Token，选择 1、7 或 30 天的平台保存期限，明确勾选加密保存同意后保存。
4. “已保存，凭据尚未验证”只表示配置持久化成功。核对结果在构建记录中查看；没有待定构建时不会为了验证 Token 而发起 GitHub 查询。
5. 支持新时间字段的版本可显示“最早再次核对时间”。它是调度等待条件，不保证准时执行；到期后的批次容量、网络耗时也可能延后执行。点击“刷新配置”更新信息。

默认调度启动延迟一分钟、批次间隔 30 秒，每批至多检查五个应用，每个应用一次处理一条待定构建。每个应用有独立的查询间隔，限流会延后核对；不要按 30 秒批次间隔推断所有应用都每 30 秒得到新结果。

自动核对可能将匹配的待定构建记为失败或取消，并进入已配置的构建失败通知流程。它不触发发布或 GitHub 重跑。查询期间如果凭据、仓库配置或构建状态改变，过时结果会被丢弃。

V36 起增加结果来源记录：如果最终失败/取消来自 GitHub 只读核对，后续有效签名的最终构建回调可以补正该记录（例如 workflow 仅因回调发送失败而失败）。成功回调仍须通过提交、分支、测试、扫描和不可变镜像校验，只会进入待人工确认，不会部署。已收到的签名最终结果不能被后续回调覆盖，迟到的 RUNNING 也不能恢复终态。升级必须实际执行 V36 及后续适用迁移；迁移不会猜测旧终态的来源，旧记录保持不可覆盖。已部署该迁移不等于这一真实异常场景已验收。

## 恢复丢失的成功构建回调

2026-09-07 已在专用私有验收仓库验证开始/结束回调均返回 404 的完整丢失场景：原构建 `34038096535` attempt 2 的 quality/security/image 成功，但平台没有该 attempt 记录；恢复地址后，`recover_build` 任务 `34076178258` 补报原制品并进入待人工确认。再次运行恢复任务仍复用同一构建记录，发布历史及运行容器不变。此证据不覆盖已有记录被 GitHub 核对判失败后的补正分支，也不代表 GitLab 已验证。

前提：后端已升级 V36，仓库已合并包含 `recover_build` 的模板，原 push 构建使用新版带 attempt 的制品。先修复回调 URL、网络和 build-status 环境密钥，不能通过恢复任务绕过连接故障。

以下步骤针对自动接入生成的**单应用** workflow。DevPilot 主仓库自身的三组件 workflow 使用不同的任务名称和 Web 制品，不能混用构建 Run ID；见 [平台自身流水线](platform-workflow.md)。

1. 在同一 workflow 的默认分支点击 Run workflow，选择 `operation=recover_build`，填写原构建 `build_run_id`；无需填写人工发布确认 ID。
2. 任务读取该 Run 当前 attempt，要求它是同仓库、同 workflow、配置分支上的已结束 push。通过 GitHub 的指定 attempt jobs 接口，分页核对 quality、security、image 三个任务，每项必须唯一、提交和 Run 匹配且成功。失败、取消、跳过、缺失或重复的门禁均停止恢复。
3. 下载原 attempt 制品，校验 repository、branch、event、runId、runAttempt、commit、image 和 digest，然后使用仅构建状态密钥补报原构建 ID。不会 checkout、构建镜像、创建应用或触发生产部署。
4. 返回 DevPilot 查看原构建是否进入待人工确认，再按正常发布流程确认，使用 `operation=release` 和生成的人工确认 ID 发布同一 digest。恢复任务本身的绿色结果不是上线成功。

旧制品、不受支持的改名/矩阵任务、已过期或已删除制品不能由这个入口恢复；不要手工改名伪装。对于已有签名失败终态或 V36 之前来源不明的失败记录，后端保持终态，恢复任务会因响应不符合待确认状态而失败，需要修正原因后进行新的构建。本功能不是后台自动扫描所有 GitHub 历史构建；仍需人工选择一次恢复操作。

## 看到不同结果怎么办

- **仍在运行**：查看核对时间。观察过期或时间异常时应重新核对，不能当作任务仍在运行的证明。
- **失败或取消**：打开对应 GitHub 运行日志，查清测试、扫描、构建或取消原因；需要重跑时去 GitHub 操作。DevPilot 核对按钮不会重跑。
- **成功但缺构建证据**：检查生成 workflow 中的构建状态上报任务、回调 URL、对应状态密钥和网关路径。修复后由受支持的流水线上报完整证据；不要手工改数据库或把测试/扫描状态直接改成通过。当前核对功能不会自动从 GitHub 恢复丢失的镜像证据。
- **凭据或权限问题**：检查 Token 本身有效期、仓库可见范围和 Actions 读取权限，再轮换平台保存的查询凭据。不需要为了查询而公开仓库或镜像。
- **限流**：遵守等待提示，避免连续手动查询。反复保存凭据不会清除自动查询的等待时间。
- **无法访问指定运行**：检查仓库和权限，并确认运行仍存在。404 不能独立证明任务不存在或构建失败。
- **网络异常或超时**：检查 DevPilot 后端到 `api.github.com:443` 的出站连接；这与 GitHub 到 DevPilot 的入站回调连接是两条不同路径。不要因为查询超时就判定应用离线。
- **证据不匹配**：核对仓库、分支、commit、运行 ID 和运行次数。不同重跑次数的结果不能混用。

## 轮换、关闭与保存结果不确定

更新 Token 前先刷新配置；保存使用版本检查，旧页面不能覆盖后来修改。新凭据不清除已有查询间隔或限流等待。平台保存期限与 Token 自身有效期是两件事，任一到期都会影响查询。

若保存或删除请求超时，先点击“刷新配置”读回真实状态，不能直接重复提交。刷新、关闭或退出页面不会撤销已经到达服务端的写操作。

“关闭并清除凭据”删除平台数据库里的当前副本并停止后续查询，不会在 GitHub 撤销 Token。需要彻底撤销时应在 GitHub 端处理；既有备份可能仍含加密副本，需遵循备份保留策略。到期后平台停止查询，后台清理任务按周期清除过期密文，并非到期瞬间立即擦除所有副本。

## 验收边界

源码级、H2/MockMvc、浏览器组件替身以及隔离 MySQL 升级恢复已有测试，不能代替真实 GitHub 网络与新版 CI/CD 发布验收。本功能不覆盖 GitLab、GitHub Enterprise 自定义域名、没有首次构建记录的任务发现或任意历史记录修复。
