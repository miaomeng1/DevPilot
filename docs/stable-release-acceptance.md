## 运行前提与边界

- 首要支持 GitHub Actions + GHCR + Dokploy；GitLab、Coolify 等兼容路径未经完整真实验收，不扩大声明。
- 真实主机运行验收为 Ubuntu 24.04 ARM64；amd64 已构建、扫描并在 GitHub Linux runner 跑测试，不等于逐个发行版完整安装认证。
- 根目录 Dockerfile 的单服务项目是自动接入主路径。不自动推断数据库迁移、持久卷和多服务依赖；平台备份不包含业务数据库/业务卷。
- 私有 Registry 需要有效读取授权；公网 CI 需要可达的 HTTPS 签名回调地址。个人电脑验收隧道不属于正式部署方案。
- 主机时间需正确 UTC/NTP。曾观察到本机 VPN 路由截走 VM 流量和测试容器 DNS 故障；只为验收连接绑定 VMware 网卡/给新测试容器设置 DNS，未修改用户 VPN 或全局路由。
- 本地备份/独立恢复不等于异地灾备；正式使用应将加密备份复制到独立设备或自有受保护存储并定期演练。
- 稳定版是明确范围的工程验收，不是零缺陷、任意负载、所有断电/网络组合或长期 SLA 保证。

## 保留策略与资源收尾

- MySQL 指标样本由代码按 7 天清理；发布、回滚、审计与通知历史没有自动 TTL，默认保留，需结合磁盘监控和定期备份管理容量，不能把“列表仅显示最近若干条”当成旧数据已删除。
- 容器日志遵循 Docker 的日志驱动/轮转策略，平台不会替 Docker 自动清理宿主日志。生产部署前配置轮转，见部署指南；长期保留日志需另配日志存储。
- 临时 `devpilot-stability-0906-r2` 已撤销，旧 Key 实测 401；两个验收仓库四个 Environment 的 8 个回调 Secrets 已删除并核对为空。临时公网隧道、回调网关及通知接收器已停止，测试通知订阅禁用。
- 保留用户原有 Dokploy Key、Registry 配置和既有演示业务。演示仓库如需再次发布，必须重新配置授权与回调，清理后的验收链路不宣称仍自动运行。
- 新增验收环境停用时保留恢复数据与受保护备份；不做全局 Docker prune，不删除既有业务卷。临时数据库和验证身份只保存在受保护的本地验收目录，不进入发行包。

后续仅安排正常缺陷修复、依赖升级及定期备份演练；Kubernetes、灰度、多服务编排等不是本阶段未完成项。
